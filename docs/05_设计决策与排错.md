# 10. 设计决策记录

这一章记录「为什么这么做」。每条都是踩过坑之后的结论，不是先验设计。

---

## 10.1 为什么是两个分区，不是三个

**决定：** AI 精选 8 件 + 更多选项 22 件，共 30 件。没有「备选礼物」分区。

**原话：**

> 「那就不需要备选礼物了，即使有合适依据的卡片一并放到更多选项里面，
> 如果卡片上有东西可写就写，没东西写就算，然后 ai 精选到 8 件」

**原因：** 「备选礼物」这个分区要成立，每张卡都得有可核实的依据。
4180 件目录里带 `risk_notes` 的太少 —— 实测 20 张里只凑得出 4 张。
为了凑数量给没依据的卡编文案，就是「模板文案冒充模型文案」，这个 bug 之前修过。

**代码里的原话**（`web/app.js:442-446`）：

> 两段而不是三段：本地规则卡一律进「更多选项」，不再单独拆「备选礼物」。
> 理由是「备选礼物」要成立必须每张都有可核实依据（留意/禁忌提示），而
> 4180 件目录里带 risk_notes 的太少——实测 20 张里只凑得出 4 张。为了凑
> 数量给没依据的卡编文案，就是之前修掉的「模板文案冒充模型文案」。
> 所以按用户的意思：卡上有东西就显示，没有就只显示价格，统一沉到更多选项。

## 10.2 为什么本地先出、AI 后补

**决定：** `/api/recommend` 同步返回本地 30 张卡（0.6 秒），
同时起后台线程调 Dify，前端轮询。

**原因：** Dify 要跑 35–90 秒。同步等待的话用户盯着空白页一分钟，
多数人会以为坏了直接关掉。

**代价：** 用户可能在 AI 结果回来前就开始看本地结果。
所以「更多选项」的提示语会根据 AI 状态变。

**为什么不做成 WebSocket / SSE：** 轮询足够，且 SSE 在 `ThreadingHTTPServer`
上要自己实现，复杂度和收益不成比例。

---

## 10.3 为什么 AI 顾问和 Dify 并行

**决定：** `_run_dify_job` 里先起顾问线程，再发起 Dify，两者并行。

**代码里的原话：**

> 顾问与 Dify 并行：顾问要等 10~20 秒，放在 Dify 后面串行会把它整段加到
> 用户等待时间上（审计实测约 18 秒）。这里在发起 Dify 之前就起线程，
> 墙钟时间取两者较大值，等于顾问白送。

**为什么顾问的问题里不带候选清单：**

> 曾经带过（用本地预览候选），结果顾问点评的是预览那三件、
> 页面展示的是 Dify 排序后的另外三件，两边对不上 —— 比不提醒更糟。
> 而等 Dify 回来再问就成了串行，白拿 18 秒。所以顾问只回答场景本身
> （关系/场合/地域/已定避开项），它对哪件礼物都成立；单件商品的注意事项
> 由卡片上的 watch_out / taboo_notes 承担。

**这是个典型的「看起来能优化，实际会让体验变差」的例子。**

## 10.4 为什么策略按礼物类型分别排名

**决定：** `strategy`（稳妥款 / 心意款 / 特别款）按每种礼物类型内部排名分配，
不按全局索引。

**代码里的原话**（`app.py:3111-3113`）：

> strategy 按每种礼物类型的序号分配，不按全局索引 —— 否则 DIY 卡片会
> 全部落在 practical，语义上的颜色区分就没了。

**具体做法**（`app.py:3103-3109`）：

```python
strategy_pool = (
    ("safe", "稳妥款"),
    ("heart", "心意款"),
    ("special", "特别款"),
    ("safe", "稳妥款"),
    ("heart", "心意款"),
)
```

按类型内部序号取模。第 6 个之后落到 `("practical", "也可以")`。

## 10.5 为什么预览卡不填 meaning / why_this

**决定：** 本地预览生成的卡片，`meaning` 和 `why_this` 留空。

**代码里的原话**（`app.py:3178-3182`）：

> 预览的 meaning / why_this 留空 —— 否则 enrich 会把模板文案
> 当成模型文案，覆盖掉 Dify 真给的文案。

**这是一个防御性设计。** `enrich_dify_result` 的逻辑是「有值就不覆盖」，
如果预览阶段填了模板文案，Dify 的真实文案就进不来了。
用户看到的就是「AI 精选」区里全是模板话。

---

## 10.6 为什么用 `selected_by` 而不是别的方式区分

**决定：** 每张卡带一个 `selected_by` 字段，`llm` 或 `local_rule`。

**为什么不用 `meaning` 有没有值判断：** 22 张本地卡里有些也有 `meaning`
（来自 `engine.py` 的 `_gift_meaning`）。用字段有无判断会误判。

**为什么不用 `rank`：** 只有 AI 卡有 `rank`，但合并过程中可能被清掉。

**`selected_by` 是唯一可靠的判据。**

---

## 10.7 为什么不用 `urllib` 访问本机

**决定：** 测试脚本访问 `127.0.0.1:8787` 时用裸 socket 或 Playwright，
不用 `urllib.request`。

**原因：** `urllib.request` 会走系统代理设置。这台机器配了代理，
`urllib` 把本机请求也发到代理上，然后超时。

**但 `urllib` 访问 `127.0.0.1:47173`（Codex Edge Control Bridge）是正常的** ——
那个端口不走代理。

---

## 10.8 为什么 `start_dify_web.ps1` 不许有中文

**决定：** 启动脚本里所有注释必须是 ASCII。

**原因：** PowerShell 5.1 读无 BOM 的 UTF-8 脚本按 GBK 解析。
中文注释会让解析失败，脚本**无任何输出直接退出**。

这个坑踩了两次。第一次以为是 Python 找不到，第二次以为是端口占用，
实际是脚本压根没跑起来。

**代码里留了警告**（第 55–57 行）：

```
# NOTE: keep every comment ASCII. PowerShell 5.1 reads a BOM-less UTF-8
# script as GBK; non-ASCII comments corrupt the parse and the launcher
# dies with no output at all.
```

## 10.9 为什么 `Start-Process` 要重定向 stdout

**决定：** 启动器里 `Start-Process` 必须带 `-RedirectStandardOutput` 和
`-RedirectStandardError`。

**原因：** 不重定向的话，子进程继承调用方的管道句柄，
命令永远不返回 —— 看起来像卡死，实际后端已经起来了。

**顺带的好处：** 重定向到 `server.log` / `server.err.log` 之后，
Python 的 `print` 输出（包括 `[dify-usage]` 这种诊断行）才留得下来。
之前性能优化全靠猜，就是因为这些输出丢了。

## 10.10 为什么检测占位密钥

**决定：** 加 `_looks_like_placeholder()` 和 `dify_config_problem()`，
在调用 Dify 之前就拦住占位密钥。

**原因：** 线上 `.env` 里写着 `DIFY_API_KEY=在这里填你的推荐工作流密钥`。
旧代码只检查「非空」，于是把 13 个中文字符塞进 HTTP 头，
`http.client` 在 latin-1 编码时抛：

```
'latin-1' codec can't encode characters in position 7-19: ordinal not in range(256)
```

**这个错误完全看不出问题在哪。** 用户看到的是「AI 不可用」，
日志里是一串编码错误。

**修复后：** `/api/health` 的 `config_problem` 直接说「密钥看起来是占位文字，
请填入 app- 开头的真实密钥」。

**教训：** 配置错误的报错信息要指向「该改哪里」，不是指向「哪里炸了」。

---

## 10.11 为什么保持 Python 3.6 兼容

**决定：** 不用 3.7+ 的语法和标准库。

**原因：** 阿里云 Linux 3.2104 自带的 `python3` 就是 3.6.8。
`dnf install python39` 在这个系统上直接报 `No match for argument: python39`。

**两处必须的兼容处理：**

1. **`ThreadingHTTPServer`（3.7+）**
   ```python
   try:
       from http.server import ThreadingHTTPServer
   except ImportError:
       import socketserver
       from http.server import HTTPServer
       class ThreadingHTTPServer(socketserver.ThreadingMixIn, HTTPServer):
           daemon_threads = True
   ```

2. **`str.isascii()`（3.7+）**
   ```python
   # 原：if not brand.isascii():
   if not all(ord(ch) < 128 for ch in brand):
   ```

**不要为了「代码更现代」把它改回去。** 改了服务器上就跑不了。

## 10.12 文案的语气规矩

这部分不在代码里，但是产品的一部分，接手的人需要知道。

**用「你」，不用「您」。**

**不暴露内部实现。** 不说「app.py」「知识库」「约束」「检索」「后端」。

**不用公文腔。** 不说「请重试」「请稍后」「请刷新」。

**店员口吻 = 第一人称讲自己的判断 + 点名具体物件 + 主动说一句提醒 + 不推销。**

**不用感叹号。**

**页脚：** `GiftRight · 送对了，比送贵了重要`

**降级提示的原话**（`web/app.js:699`）：

> 这次先给你快速结果
>
> AI 那边没回应，下面这些是按你的条件筛的，照样能挑。想再试一次，重新提交就行。

**注意这句的结构：** 先安抚（照样能挑），再给行动（重新提交就行），
没有道歉也没有技术解释。

## 10.13 为什么不给卡片自动选中第一件

**决定：** 结果页出来时不预选任何卡片。

**代码里的原话**（`web/app.js:457-458`）：

> Market Ready：不自动替用户选中第一件。只在「新结果首次渲染本页」时清空，
> 用户点选触发的重渲染、翻页、AI 更新都不清 —— 否则点击会被自己的重渲染吞掉。

**两个要点：**
1. 不预选 —— 替用户做决定是越界
2. 清空只在「新结果首次渲染」时做 —— 否则用户点了卡片，
   重渲染又把选中状态清掉，看起来像点了没反应

---

## 10.14 分页只切「更多选项」

**决定：** AI 精选整段固定在顶部，分页只作用于「更多选项」。

**代码里的原话**（`web/app.js:448-451`）：

> 分页只切「更多选项」，AI 精选整段固定在顶部。原来先合并再按 6 件切片，
> AI 精选有 8 张时第 1 页被精选占满、「更多选项」一个都不出现，第 2 页又
> 接不上精选 —— 用户看到的是「只有 AI 精选」或「精选被拆成两半」，
> 跟「两个分区」的设计对不上。

**每页 6 件。**

---

## 10.15 「AI 没有返回精选」只在真的跑完才说

**决定：** AI 还在跑的时候，不显示「AI 没选出」。

**代码里的原话**（`web/app.js:473-474`）：

> "AI 没有返回精选"只在 AI 真的出完结果且一件没选时才说；
> 增强还在跑的时候只说本地结果，不提前下结论。

**还有一个细节**（`web/app.js:476-478`）：

> AI 是否真的有选，看全量候选而不是当前页——LLM 卡集中在第 1 页，
> 翻到后面页时不能误报"AI 没有选出"。

# 附录 A：快速排错

| 症状 | 最可能的原因 | 怎么查 |
|---|---|---|
| 页面打不开 | 只监听 127.0.0.1 | `curl 127.0.0.1:8080/api/health` 通但外网不通 → 加 `GIFT_RIGHT_HOST=0.0.0.0` |
| `configured: false` | 密钥缺失或占位 | 看 `/api/health` 的 `config_problem` |
| `'latin-1' codec can't encode` | 密钥含中文 | 同上 |
| AI 一直不回来 | Dify 超时或报错 | `journalctl -u giftright -f`，看 `[dify-usage]` 行 |
| 30 张卡全是本地 | Dify 调用失败 | 看响应里的 `dify_error` |
| 卡片显示「未命名候选」 | 知识库 md 没读到 | 确认 `data/dify_uploads/` 两个 md 文件在 |
| 启动器无输出直接退出 | 脚本里有中文 | 检查 `start_dify_web.ps1` 是否全 ASCII |
| 改了 `app.py` 不生效 | 启动器硬编码覆盖 | 改 `start_dify_web.ps1` 第 58–60 行 |
| 服务 `active` 但外网不通 | 安全组没放行 | 阿里云控制台加 8080 入方向 |
| 轮询报 `WinError 10060` | 连接队列满 | 放宽轮询间隔到 2 秒以上 |
| 重启计数一直涨 | `nohup` 和 systemd 抢端口 | 只留 systemd，`systemctl reset-failed` |
