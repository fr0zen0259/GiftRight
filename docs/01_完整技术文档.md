# 1. 五分钟跑起来

## 1.1 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| Python | **3.6 及以上** | 已在 3.6.8（阿里云 Linux）和 3.13.9（Windows）实测通过 |
| Node.js | 不需要 | 前端是原生 JS，无构建步骤 |
| 第三方 Python 包 | **零个** | 全部用标准库 |
| 浏览器 | 支持 ES2020 的现代浏览器 | Chrome / Edge / Safari 均可 |

**这个项目刻意做到零依赖。** `app.py`、`engine.py`、`dify/rule_node_final.py` 只 import 标准库。
所以不需要 `pip install`，不需要 `requirements.txt`，也不需要虚拟环境。

## 1.2 配置密钥

复制 `.env.example` 成 `.env`，填入两个 Dify 密钥：

```bash
DIFY_BASE_URL=https://api.dify.ai
DIFY_API_KEY=app-你的推荐工作流密钥
DIFY_CHAT_API_KEY=app-你的对话应用密钥
```

**这两个密钥从哪来：**

1. 登录 Dify（https://cloud.dify.ai 或你自己部署的实例）
2. 打开你的应用 → 左侧「访问 API」
3. 复制 `app-` 开头的那串密钥

**⚠️ 密钥必须以 `app-` 开头。** 如果填了中文或占位文字，程序会检测出来并拒绝调用，
`/api/health` 会返回 `configured: false` 并附上中文说明。
（早期版本没有这个检测，直接抛出 `'latin-1' codec can't encode characters` 这种
看不出问题的错误。）

**没有 Dify 也能跑。** 不填密钥时服务进入 `local_rule_mode`，
靠本地规则引擎出结果，只是没有 AI 精选那 8 件。适合先看界面。

## 1.3 启动

**⚠️ 先记住一件事：`app.py` 自己不读 `.env` 文件。**

它只从**进程环境变量**里读配置。`.env` 只是给人看的存档，
必须有东西把里面的值注入到环境变量里 —— 启动器、systemd、或 `export` 都行。
直接 `python3 app.py` 会拿不到密钥，静默降级成本地规则模式。

**Windows：**

```powershell
cd GiftRight_reproduction_package
powershell -NoProfile -ExecutionPolicy Bypass -File .\start_dify_web.ps1
```

启动器会读 `.env`，把 `DIFY_API_KEY` / `DIFY_CHAT_API_KEY` 注入进程环境，再起 Python。

**Linux / macOS（手动）：**

```bash
cd GiftRight_reproduction_package
set -a && . ./.env && set +a
python3 app.py
```

`set -a` 让后续所有赋值自动 export，`. ./.env` 把文件当 shell 脚本执行。

**Linux（生产，systemd）：**

```ini
EnvironmentFile=/opt/giftright/.env
ExecStart=/usr/bin/python3 -X utf8 app.py
```

`deploy.sh` 就是这么配的。systemd 负责注入，不用 `source`。

打开 http://127.0.0.1:8787 即可。

## 1.4 验证跑通了

```bash
curl http://127.0.0.1:8787/api/health
```

正常输出：

```json
{
  "ok": true,
  "version": "gift-right-2.1",
```

# 2. 这个项目到底在做什么

## 2.1 一句话

用户填一份问卷（送给谁、什么场合、预算多少、有什么忌讳），
系统从 4180 件真实商品里挑出 30 件，其中 8 件由 AI 精挑并写上推荐理由。

## 2.2 用户看到的流程

```
首页（选场景）
   ↓
四步问卷
   第 1 步：场合（生日 / 答谢 / 毕业 / 入职 / 纪念日 / 节日 / 其他）
   第 2 步：关系（导师 / 领导 / 同事 / 朋友 / 伴侣 / 家人 / 同学 / 其他）
           + 收礼人偏向（偏男性 / 偏女性 / 不指定）
   第 3 步：预算区间 + 偏好标签（不饮酒 / 清真 / 素食 / 避免动物制品 /
           避免香味 / 注意过敏原）+ 自制还是买成品
           + 对方在哪个省 / 你在哪儿
   第 4 步：自由描述 + 有什么千万别送的
   ↓
提交
   ↓
0.6 秒 → 立刻看到 30 张卡（本地规则筛的，此时 AI 精选区显示「我还在挑」）
   ↓
35–90 秒 → AI 精选区出现 8 张卡，带推荐理由
```

## 2.3 两个分区（这是硬性设计要求）

结果页**只有两个分区**：

| 分区 | 标题 | 内容 | 数量 |
|---|---|---|---|
| 1 | 我先挑的 | AI 从合规候选中精选，每张带 `meaning` 和 `why_recommended` | 8 件 |
| 2 | 更多选项 | 本地规则筛出的其余候选 | 22 件 |
| | **合计** | | **30 件** |

**没有第三个「备选礼物」分区。** 这是用户明确要求的：

> 「那就不需要备选礼物了，即使有合适依据的卡片一并放到更多选项里面，
> 如果卡片上有东西可写就写，没东西写就算，然后 ai 精选到 8 件」

原因：要成立「备选礼物」这个分区，每张卡都得有可核实的依据（风险提示、禁忌提示）。
但 4180 件目录里带 `risk_notes` 的太少 —— 实测 20 张里只凑得出 4 张。
为了凑数量给没依据的卡编文案，就是「模板文案冒充模型文案」，
而这个 bug 之前修过。所以干脆不设这个分区。

**分页只切「更多选项」，AI 精选整段固定在顶部。**
早期版本先把两个区合并再按 6 件切片，导致 AI 精选 8 张时第 1 页被精选占满、
「更多选项」一件都不出现，用户看到的是「只有 AI 精选」。现已改掉。

## 2.4 核心设计：本地先出，AI 后补

这是整个系统最重要的一个决定。

```
用户提交
   ↓
同步：本地规则引擎筛 30 件 ────────→ 0.6 秒后页面就有内容
   ↓
异步：起后台线程调 Dify ──────────→ 35–90 秒后覆盖 AI 精选区
```

**为什么这么做：** Dify 工作流要跑 35–90 秒。如果同步等待，
用户盯着空白页面等一分钟，多数人会以为坏了直接关掉。
先给结果再补 AI，等待期间页面是满的。

代价是：用户可能在 AI 结果回来之前就开始翻看本地结果。
所以「更多选项」区的提示语会根据 AI 状态变化：

| AI 状态 | 提示语 |
|---|---|
| 还在跑 | 我还在挑，这些是先从里面筛出来的 |
| 跑完了，有精选 | 这些也不错，就是不那么对得上 |
| 跑完了，一件没选 | 这轮没挑出特别合适的，下面是按你的条件筛的 |

## 3.2 三条并行线为什么这么排

`_run_dify_job` 里，AI 顾问和 Dify 是**并行**的，不是串行。

代码里的原话：

> 顾问与 Dify 并行：顾问要等 10~20 秒，放在 Dify 后面串行会把它整段加到用户等待时间上
> （审计实测约 18 秒）。这里在发起 Dify 之前就起线程，墙钟时间取两者较大值，等于顾问白送。

**顾问的问题里不带候选清单。** 这个决定也踩过坑：

> 曾经带过（用本地预览候选），结果顾问点评的是预览那三件、
> 页面展示的是 Dify 排序后的另外三件，两边对不上 —— 比不提醒更糟。
> 而等 Dify 回来再问就成了串行，白拿 18 秒。所以顾问只回答场景本身
> （关系/场合/地域/已定避开项），它对哪件礼物都成立；单件商品的注意事项
> 由卡片上的 `watch_out` / `taboo_notes` 承担。

## 3.3 三个数量上限

```python
# app.py:64-66
DIFY_CANDIDATE_LIMIT    = int(os.getenv("DIFY_CANDIDATE_LIMIT", "36"))
PREVIEW_CANDIDATE_LIMIT = int(os.getenv("GIFT_RIGHT_PREVIEW_LIMIT", "60"))
DISPLAY_CANDIDATE_LIMIT = int(os.getenv("GIFT_RIGHT_DISPLAY_LIMIT", "30"))
```

| 常量 | 默认 | 含义 |
|---|---|---|
| `PREVIEW_CANDIDATE_LIMIT` | 60 | 本地预览池大小，从 4180 件里挑 60 件 |
| `DIFY_CANDIDATE_LIMIT` | 36 | 喂给 Dify 的候选数 |
| `DISPLAY_CANDIDATE_LIMIT` | 30 | 页面显示总数 |

**⚠️ 两个陷阱：**

1. **`.env.example` 里的值是错的。** 它写着 40/20/24，是旧版本的遗留。
   代码默认值是 60/30/36。以代码为准。
2. **`start_dify_web.ps1` 里硬编码了这三个值**（第 58–60 行）。
   只改 `app.py` 的默认值不生效 —— 启动器会盖掉。**两处必须同步改。**

这个坑踩过一次：改完 `app.py` 重启后行为完全没变。

**四个必须知道的实现细节：**

1. **`DIFY_JOBS = {}` 是进程内存**（第 86 行）。
   所以这个服务**不能跑多副本**，也不能用纯 serverless —— 提交和轮询必须打到同一个进程。
   任务 900 秒后清理。

2. **`_EMPTY_DUMP_PATH` 是调试钩子**（第 78 行）。
   设置环境变量后会把空结果 dump 到文件。生产环境不要设。

3. **默认只监听本机**（第 4580 行）：
   ```python
   HOST = os.getenv("GIFT_RIGHT_HOST", "127.0.0.1").strip() or "127.0.0.1"
   ```
   云端必须设 `GIFT_RIGHT_HOST=0.0.0.0`，否则外部访问不到。
   这个坑在部署时踩过：服务显示 `active (running)`，但外部连不上。

4. **端口默认 8787**（第 63 行）。云端通常改成 8080。

**`start_dify_web.ps1` 有两个硬性约束：**

1. **文件里不许出现非 ASCII 字符。** PowerShell 5.1 读无 BOM 的 UTF-8 脚本按 GBK 解析，
   中文注释会让整个脚本解析失败，启动器**无任何输出直接退出**。这个坑踩了两次。
2. **`Start-Process` 必须重定向 stdout/stderr。** 不重定向会持有调用方管道，
   命令永远不返回，看起来像卡死（实际后端已经起来了）。
