# 7. 数据结构契约

前端、后端、Dify 之间靠 JSON 传递数据。这一章把每一层的字段写清楚。

**字段名写错是这个项目最常见的 bug 来源。** 有几处命名不一致是历史遗留，
改不动也不想改，记住就行。

---

## 7.1 前端 → 后端：推荐请求

`POST /api/recommend`

```json
{
  "occasion": "birthday",
  "recipient_relation": "friend",
  "recipient_gender": "male",
  "budget_min": 100,
  "budget_max": 300,
  "preferences": ["non_alcoholic", "avoid_fragrance"],
  "accept_food_diy": true,
  "accept_fragrance_diy": false,
  "recipient_region": "广东",
  "user_region": "浙江",
  "free_text": "他喜欢喝咖啡，别太贵",
  "avoid_custom": "别送钟"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `occasion` | string | `birthday` / `thank_you` / `graduation` / `onboarding` / `celebration` / `holiday` / `other` |
| `recipient_relation` | string | `mentor` / `manager` / `colleague` / `friend` / `partner` / `family` / `classmate` / `other` |
| `recipient_gender` | string | `male` / `female` / `""`（不指定）。**空字符串不是 null** |
| `budget_min` / `budget_max` | number | 默认 30 / 300。`budget_min > budget_max` 会被拒 |
| `preferences` | array | 见 7.2 |
| `accept_food_diy` | bool | 是否接受食品类手作 |
| `accept_fragrance_diy` | bool | 是否接受香氛类手作 |
| `recipient_region` / `user_region` | string | 省份名，用于地域禁忌和时效估算 |
| `free_text` | string | 自由描述 |
| `avoid_custom` | string | 用户自己填的「千万别送」 |

### 7.2 偏好标签取值

```
non_alcoholic        不饮酒
halal                清真
vegetarian           素食
no_animal_products   避免动物制品
avoid_fragrance      避免香味
allergy_free         注意过敏原
```

**这六个字符串是硬编码的**，前端按钮的 `value`、后端判断、Dify 提示词三处都用它们。
改一个字就全断。

## 7.3 后端 → 前端：提交响应

`POST /api/recommend` 立刻返回（约 0.6 秒）：

```json
{
  "source": "local_rule_mode",
  "dify_status": "running",
  "dify_job_id": "dify-d39f1c0f6c89",
  "result": {
    "candidates": [ ... 30 张卡 ... ],
    "page_notices": [ ... ],
    "scene_taboo": { ... }
  }
}
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `source` | `local_rule_mode` | 本地规则出的结果（AI 还没回或没配） |
| | `dify` | Dify 成功返回 |
| `dify_status` | `running` | 后台任务在跑，等轮询 |
| | `not_configured` | 没配密钥，不会跑 AI |
| | `succeeded` | Dify 成功 |
| | `invalid_structured_output_fallback` | Dify 输出不合规，降级 |
| | `empty_result_fallback` | Dify 一件没选出来，降级 |
| `dify_job_id` | 字符串 | 轮询用。**为空就不要轮询** |
| `result.candidates` | 数组 | **30 张卡在这个字段下，不是 `items`** |

**`source` 只有三个真实取值**（`app.py:4103` / `:4193` / `:4554`）：
`local_rule_mode`、`dify`，以及兜底救援时的 `_rescued_from`。
**没有 `local_preview` 这个值** —— 早期文档里写错过。

**⚠️ 第一个大坑：卡在 `result.candidates`，不是 `result.items`。**
早期版本和某些调试脚本用 `items`，读出来永远是空列表。

**⚠️ 第二个大坑：`dify_error` 只在失败时出现。**
前端据此决定要不要显示降级提示。

## 7.4 轮询接口

`GET /api/recommend/status?job_id=a1b2c3d4`

```json
{
  "dify_status": "succeeded",
  "result": { "candidates": [ ... ] },
  "dify_error": null
}
```

前端每 2 秒轮询一次，最多 180 次（6 分钟）。

**容错规则：**
- 连续 5 次请求失败才报错
- 180 次用完显示「等待超时」
- 单次失败不中止

**⚠️ 第三个坑：`request_queue_size` 默认 5。**
`ThreadingHTTPServer` 的待处理连接队列默认只有 5。Dify 跑着的时候
如果轮询间隔太短（比如 1 秒）会打满队列，客户端收到
`TimeoutError: [WinError 10060]`。现在轮询是 2 秒，够用；
但如果你写脚本压测，记得放宽间隔或者加连接重试。

```python
import re
nums = re.findall(r"\d+(?:\.\d+)?", price_str.replace(",", ""))
lo, hi = min(map(float, nums)), max(map(float, nums))
```

### 关键字段

| 字段 | 谁填 | 说明 |
|---|---|---|
| `gift_type` | 后端 | `purchased` / `diy`，决定进哪个视图 |
| `selected_by` | 后端 | **`llm` = AI 精选，`local_rule` = 更多选项** |
| `strategy` | Dify 或本地 | `safe` / `heart` / `special`；`strategy_label` 是对应中文 |
| `rank` | Dify 或本地 | 排序位次。DIY 卡在本地模式下 rank 可能是 55 这种大数 |
| `meaning` | Dify | 礼物寓意。本地卡为 `""` |
| `why_this` | 后端映射 | **前端读这个**，来源是 Dify 的 `why_recommended` |
| `reason_evidence` | 两边 | 引用商品事实的短句数组 |
| `copy_source` | 后端 | `template` = 模板文案，`llm` = 模型文案 |
| `is_llm_copy` | 后端 | 布尔，前端据此区分文案来源 |
| `watch_out` | 后端 | 一句话注意事项，可能是 `""` |
| `taboo_notes` | 后端 | 撞上的禁忌列表 |
| `risk_notes` | 后端 | 风险说明，通常是一句免责 |

### ⚠️ 三个命名不一致（重要）

**1. `selected_by` 是唯一的 AI/本地判据。**

前端 `isAiCard()` 就是读这个字段：

```javascript
function isAiCard(card) {
  return card.selected_by === "llm";
}
```

**不要用 `meaning` 有没有值判断** —— 判断不可靠。用 `selected_by`。

**2. Dify 输出 `why_recommended`，卡片上是 `why_this`。**

后端在 `enrich_dify_result` 里做了映射。**前端永远不读 `why`，那个字段不存在。**

**3. `meaning` 两边同名**，不用映射。

**记一句：AI 卡看 `selected_by`，理由看 `why_this`，寓意看 `meaning`。**

## 7.8 Dify → 后端：响应

流式响应，最后一块里：

```json
{
  "data": {
    "outputs": {
      "text": "{\"intent\":{...},\"candidates\":[...],\"card_message\":\"...\",\"ranking_version\":\"ranker-v6\"}"
    }
  }
}
```

**`outputs.text` 是一个 JSON 字符串，要再 parse 一次。**

解析出来的结构：

```json
{
  "intent": { "occasion": "...", "recipient_relation": "..." },
  "rule_result": {
    "eligible_products": ["id1", "id2", ...],
    "hard_blocks": [ ... ],
    "soft_warnings": [ ... ]
  },
  "candidates": [
    {
      "product_id": "...",
      "strategy": "safe",
      "rank": 1,
      "reason_evidence": ["..."],
      "meaning": "...",
      "why_recommended": "...",
      "risk_note": "",
      "soft_warnings": [],
      "price_estimate": { ... },
      "delivery_estimate": { ... }
    }
  ],
  "card_message": "祝你生日快乐",
  "ranking_version": "ranker-v6"
}
```

**注意 `price_estimate` / `delivery_estimate` 出现在 Dify 输出里** ——
模型不输出它们（提示词明确禁止），是代码节点 2 从规则节点数据里合并回来的。

**但这两个字段不会原样出现在前端卡片上。** 后端 `enrich_dify_result` 会把它们
压成展示字符串（`"约 179–219 元"`）写进 `price` / `cost` / `price_band`。
所以你在浏览器里永远看不到 `price_estimate` 对象。

**这是刻意设计：** 展示层只认一个字符串，避免前端到处判断嵌套结构。
代价是任何要算数的逻辑都得自己解析字符串（见 7.5 的解析函数）。

## 7.9 合并逻辑（后端核心）

`merge_dify_with_preview` 在 `app.py:3776`，是这个系统最复杂的函数。

**输入：** 本地预览的 30 张卡 + Dify 返回的候选列表
**输出：** 最终 30 张卡，其中 8 张 `selected_by="llm"`，22 张 `selected_by="local_rule"`

**做的事：**

1. 用 Dify 返回的 `product_id` 在本地候选池里找到对应商品
2. 找到的 → 打上 `selected_by="llm"`，填入 Dify 给的文案字段
3. 找不到的 → 用 `_load_kb_product_cards()` 从知识库 md 里补全事实字段
   （这就是 `KB_CARD_FILES` 的用途，防止页面出现「未命名候选」）
4. 补回 `price_estimate` / `delivery_estimate`
5. 把剩下的本地候选打上 `selected_by="local_rule"`
6. 按 `rank` 排序 AI 卡，按分数排序本地卡
7. 截断到 30 张

**`_overflow_eligible_cards` 的处理有讲究**（`app.py:3083-3092` 有注释说明）：
这个中间变量必须活到 `merge_dify_with_preview`，但它不能被 `_send_json` 序列化出去。
所以 `build_fast_preview` 包了一层。

# 8. 部署到云服务器

实测环境：阿里云 ECS，Alibaba Cloud Linux 3.2104 LTS 64 位，Python 3.6.8。

---

## 8.1 为什么选这个组合

**Python 3.6.8 是阿里云 Linux 3 自带的版本，而项目正好兼容它。**

一开始写的代码用了两个 3.7+ 的特性，在服务器上直接崩：
- `ThreadingHTTPServer`（3.7 才有）→ 加了 import 兼容层
- `str.isascii()`（3.7 才有）→ 改成 `all(ord(ch) < 128 for ch in brand)`

**这是刻意保持的兼容性。** 不要为了用新语法把它改回去，否则服务器上跑不了。

## 8.2 部署步骤

### 第 1 步：上传

```bash
# 本地
scp giftright-deploy.tar.gz root@你的服务器IP:/opt/

# 服务器
cd /opt
tar -xzf giftright-deploy.tar.gz
```

### 第 2 步：配 `.env`

```bash
cd /opt/giftright

```

**必须有的内容：**


## 8.3 systemd 配置

`deploy.sh` 会写 `/etc/systemd/system/giftright.service`：

```ini
[Unit]
Description=GiftRight gift recommendation service
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/giftright
ExecStart=/usr/bin/python3 app.py
Restart=always
RestartSec=5s
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

**`Restart=always` + `RestartSec=5s`。** 崩了自动拉起来，5 秒后。

**⚠️ 不要同时用 `nohup` 和 systemd。** 两者会抢端口，形成重启死循环
（见过重启计数到 268）。`deploy.sh` 里 `USE_SYSTEMD=1` 时不会用 `nohup`。

## 8.4 常用运维命令

```bash
systemctl status giftright          # 看状态
systemctl restart giftright         # 重启
systemctl reset-failed giftright    # 清重启计数（改过配置后建议跑）
journalctl -u giftright -f          # 看实时日志
journalctl -u giftright -n 100      # 看最近 100 行
```

**日志在 journald 里，不在文件里。** `/opt/giftright/giftright.log` 可能是空的或过时的。

## 8.5 访问控制

**默认情况下服务对所有人开放。** 想加口令就用 `GIFT_RIGHT_ACCESS_TOKEN`。

设置后，访问方式是：

```
http://你的IP:8080/?token=你的口令
```

验证通过后种一个 `gr_access` cookie，有效期 30 天，之后直接访问即可。

**三层防护：**

| 层 | 配置 | 作用 |
|---|---|---|
| 访问口令 | `GIFT_RIGHT_ACCESS_TOKEN` | 没口令打不开 |
| 限流 | `GIFT_RIGHT_RATE_LIMIT=6` | 每分钟最多 6 次推荐 |
| 失败锁定 | 硬编码 5 次 | 连续 5 次口令错，锁 5 分钟 |

**`/api/health` 是匿名可访问的**，不占限流额度。这是设计如此 ——
监控系统需要能探活，而探活不该需要口令。

## 8.6 成本

**每次推荐消耗 Dify 约 47,000–62,000 tokens**（实测五次：46991 / 51532 /
48904 / 50612 / 62484）。

按 deepseek 的定价，一次推荐大约几分钱。但如果不加限制，
被人刷起来账单会很难看。**建议在 Dify 侧也设一个每日调用上限作为兜底。**

## 8.7 性能实测

| 环节 | 耗时 |
|---|---|
| 本地预览出 30 张卡 | **0.6 秒** |
| Dify 工作流端到端 | **35–90 秒**（典型 52 秒） |
| 其中 LLM 2 排序 | 约 28 秒（占 47%） |
| 四个知识检索合计 | 约 8 秒 |
| LLM 需求解析 | 约 5 秒 |
| Card Writer | 约 4 秒 |
| 代码节点合计 | < 1 秒 |

**墙钟时间 = max(顾问, Dify) ≈ Dify 的时间**，因为两者并行。

# 9. 已知问题与限制

诚实列出。接手前应该知道这些。

## 9.1 架构限制

| 限制 | 原因 | 影响 |
|---|---|---|
| **不能跑多副本** | `DIFY_JOBS` 是进程内存（`app.py:86`） | 提交和轮询必须打到同一进程。要扩容得先把任务状态外置到 Redis |
| **不能用纯 serverless** | 同上 | 函数实例会被回收，轮询找不到 job |
| **单机单进程** | stdlib `ThreadingHTTPServer` | 并发高了会排队。`request_queue_size` 只有 5 |
| **重启丢任务** | 同上 | 服务重启时正在跑的 Dify 任务全丢，用户看到超时 |

## 9.2 数据缺陷（已知，暂不修）

用户明确说过：「如果是由于商品知识库不足的原因，请暂时放在一边，把其他问题都解决好」。

| 问题 | 详情 |
|---|---|
| **10000–20000 元价位几乎空白** | 该区间只有 2 条商品 |
| **`taboos.csv` 零条地域行** | 105 条禁忌没有一条绑定到地区，所以「地域与禁忌检索」节点实际做不了地域 |
| **男性商品严重不足** | 561/4180 = 13.4% 明显偏男性，其余中性或偏女性 |
| **价格异常** | 博朗9系剃须刀标价 1.00/2.00/3.00 元；金龙鱼调和油 ¥7–9；毛戈平气垫 ¥10–14；Viking 项链 ¥14–18；亚克力钥匙扣 ¥0–2 |
| **类目错标** | 「纳西索」（香水品牌）被归到错误的类目 |
| **知识库与目录不一致** | `06_商品事实库_合并重点名版.md` 有 7291 张卡，但本地目录只有 4180 件。Dify 可能返回本地找不到的 ID |

**「知识库与目录不一致」这条是设计上的权衡，不是 bug。**
知识库大是为了检索召回全；本地目录小是因为要控制响应速度。
`_load_kb_product_cards()` 就是为这个差距准备的 —— 从知识库补全本地没有的商品。

## 9.5 明确不要做的优化（试过，无效或有害）

这一节是从踩坑记录里来的，**别重试**：

| 想法 | 为什么不行 |
|---|---|
| 把 LLM 2 拆成并行分片 | 8 个候选拆 4 路并发，每路都要加载完整检索上下文，总 token 翻倍，反而更慢 |
| 截断候选池到 24 件 | 精选质量明显下降，且耗时几乎没变（瓶颈在输出不在输入） |
| 换更小的模型 | 文案质量断崖下降，「模板文案」问题重现 |
| 并行化四个检索 | 已经是最优，串行总耗时约 8 秒，并行省不到 2 秒还增加失败率 |
| 压缩检索元数据 | 输入 token 走 prefill（并行处理），输出走 decode（逐字生成）。省输入几乎不影响墙钟时间 |
| 收紧 `has_alcohol` / `has_nuts` | 会误杀大量正常商品 |
| 把 `ranking_version` 对齐成 v5 | 提示词要求 v6，改了会让模型输出不合规 |
| 提高 `DIFY_CANDIDATE_LIMIT` | 用户明确说「暂时先不需要提」 |
| 6+14 分区 | 用户要的是 8+22 |

**唯一真正有效的提速手段就是 v5→v6 那次：删掉 `price_estimate` 和
`delivery_estimate` 的输出要求。从 60 秒降到 52 秒。**
